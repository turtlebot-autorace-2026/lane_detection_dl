# 에이전트 작업 안내

이 파일은 이 패키지 안에서 작업하는 에이전트의 기준이다. 먼저 [README.md](README.md)로 현재 동작과 알려진 문제를 읽고, [CONTRIBUTING.md](CONTRIBUTING.md)에서 확장 절차를 확인한다. 사용자의 현재 요청과 명시된 작업 범위가 우선한다.

## 프로젝트 의도

팀원들이 각자 개발한 검출·조향 코드를 하나의 `DrivingNode`에 연결한다. 새 알고리즘을 추가할 위치와 입력부터 출력까지의 호출 순서가 코드에서 직접 보여야 한다. ROS 2 Galactic / Python 3.8 호환을 유지한다.

| 위치 | 책임 |
| --- | --- |
| `driving/driving.py` | ROS 통신, 선택 이름, 객체 생성, 파라미터 조회, 명시적인 호출 분기, 발행 |
| `driving/driving_debug.py` | 영상 6개 토픽 구독, JPEG 디코딩, OpenCV 창 표시 |
| `driving/detection/` | 알고리즘별 디코딩·전처리·ROI·검출·미검출 정책·디버그 표시본 |
| `driving/steering/` | 검출 결과를 해석하여 `Twist` 계산 |

노드의 파라미터를 함수 인자로 전달한다. 각 알고리즘은 필요한 메시지나 수치를 받아 계산하고, ROS Node 생성·구독·발행은 공통 노드에서 관리한다.

## 현재 YOLO 연결 기준

- 검출기별 조향기는 Sat/Basic_P, Sobel/Basic_P, YOLO/LanePurePursuit로 고정한다. `/driving/detection` 하나로 검출과 연결된 조향을 함께 선택하며 `/driving/steering` 구독·상태·조합 검사는 없다. 기본 선택은 YOLO이며 주행은 초기 비활성이다. 검출·조향 계산과 디버그 발행은 대기 중에도 수행하고 `/lane_state=true`로 전환한 뒤 새로 수신한 영상부터 주행 속도를 발행한다. 새 알고리즘도 해당 분기에서 조향기를 직접 호출한다.
- YOLO 입력은 보정된 `/camera` 압축영상이다. 원본의 640×480 BEV, `LanePath.target()` → `PurePursuit.compute_to()` 순서, 모델 클래스 0 white/1 yellow를 보존한다. basic의 ROI나 픽셀 중심으로 대체하지 않는다.
- 검출 출력 `(target, mode)`의 target은 차축 기준 전방 x/좌측 y의 미터 좌표 또는 None이다. mode는 both/yellow_only/white_only/lost다. 정상 미검출은 기본 0.05m/s 직진, 한쪽 검출은 속도 0.8배이며 입력/추론 오류의 정지와 구분한다.
- `/lane_state` Bool은 모든 차선 알고리즘의 주행 허용을 제어한다. 초기 False이며 camera_callback과 process_yolo의 정상·오류 속도 발행에 `lane_enabled` 검사를 둔다. 대기 상태를 이유로 검출·조향 계산이나 디버그 발행을 건너뛰지 않는다. False 수신마다 0 Twist를 발행하고 YOLO 미처리 영상·추적·평활화를 비우며 이후 영상으로 계산 상태는 다시 갱신된다. False→True에서는 미처리 영상만 비우고 추적·평활화는 유지한다. 반복 True는 미처리 영상도 유지하고 검출 선택은 주행 허용을 바꾸지 않는다. 새 입력 콜백/타이머에도 같은 발행 조건과 재개 시 미처리 영상 폐기, 필요한 정지 초기화를 연결한다. 명시적 정지·검출 선택 변경·정상 종료의 0 Twist는 유지한다. 외부 미션 패키지가 이 토픽을 발행한다. 미션 노드는 이 패키지 안에 추가하지 않는다.
- `/intersection_state` Bool은 노드가 받아 YOLO 조향에만 전달한다. 교차로에서는 `pure_pursuit.v_max_intersection`(현재 기본 0.30)과 원본 내부 곡률 배율 0.7을 사용한다. 원본처럼 교차로 전환 자체는 추적·평활화를 초기화하지 않고, 미검출은 `v_lost`, 한쪽 차선은 `v_single` 정책을 유지한다. 기본 교차로 상태는 False이며 알고리즘 변경에도 마지막 수신값을 유지한다. 내부 검출 mode와 외부 enable을 혼동하지 않는다. 기존 Basic_P에 사용자가 남긴 교차로 주석은 별개로 보존한다.
- YOLO만 최신 수신 메시지 + 기본 15Hz 타이머로 처리한다. 같은 메시지 재처리와 카메라 콜백의 중복 추론을 피한다. 타이머는 단일 executor 안에서 동기 실행되므로 실제 15fps나 비차단 수신을 보장하지 않는다.
- 모델은 첫 사용에 한 번 로드하고 재사용한다. 검출 선택 변경은 정지 발행 후 대기 영상·추적·조향 평활화를 초기화한다. 새 조향기를 추가할 때 해당 검출 분기의 호출부와 필요한 상태 초기화를 연결한다.
- 원본 설정은 노드의 ROS 파라미터로 유지한다. 모델 경로·장치·주기는 시작 전용 read_only이고 나머지 튜닝값은 프레임마다 읽는다. 창 표시 설정은 제거했다. 유효 범위 검사와 실제 적용 시점을 문서에 적는다.
- 주행 노드와 알고리즘은 디버그 영상 생성·JPEG 토픽 발행만 담당한다. GUI 창·키 입력 코드는 별도 `driving_debug` 노드에만 둔다. 뷰어는 `IMAGE_TOPICS`의 camera/camera_raw/camera_raw_16_9/camera2/debug1/debug2를 구독하며 속도·알고리즘 선택을 발행하지 않는다. 새 영상 토픽이 생기면 목록과 문서를 함께 갱신한다.
- YOLO 디버그는 원본 draw와 입력 header를 보존한다. 모델 출처·해시는 models/README.md, 설치 경로는 setup.py의 share data_files를 확인한다. 기본 YOLO 주행에는 추론 의존성이 필요하다. Ultralytics는 대기 중에도 첫 YOLO 처리 때 import한다. basic만 사용할 환경에서는 카메라 입력 전에 basic으로 전환해야 모델 로드를 피할 수 있다.

## 외부 미션 연결 기준

- 미션 노드는 사용자가 지정한 외부 저장소의 패키지를 사용한다. 이 패키지에 미션 구현·실행 엔트리·미션 전용 디버그 발행을 복제하지 않는다.
- `/lane_state`와 `/intersection_state` 구독을 통해 외부와 연결한다. 현재 `/lane_mode`와 `/traffic_light_state`를 구독하지 않으며 이식되지 않은 방향 제어를 지원한다고 설명하지 않는다.
- 원본 신호등 시작 신호는 주행 정지 명령과 다르다. 초기 대기 또는 명시적인 lane False 이후 외부 미션을 시작한다. 외부 패키지의 판정·자기 상태 재발행·GUI·종료 코드를 이 패키지의 기능/검증 결과로 취급하지 않는다.
- 뷰어의 `/camera2` 입력은 유지한다. 외부 미션의 디버그 영상 토픽이 실제로 생기면 별도 요청 범위에서 구독을 연결한다.

## 수정 원칙

- 현재 요청을 완료하는 작은 변경부터 한다. 설명·검토 요청을 전체 구현이나 리팩터링 승인으로 확대하지 않는다.
- 기존처럼 import, 선택 목록, 객체 생성, 카메라 콜백의 명시적 분기를 통해 연결한다. 목록에 이름을 추가했으면 실제 호출도 연결한다.
- 반복되는 동일 작업은 작은 함수로 묶을 수 있다. 알고리즘 추가를 이유로 등록 시스템, 공통 기반 클래스, 범용 결과 객체, worker, 자동 호환성 계층을 일괄 도입하지 않는다. 실행 구조 변경은 필요한 이유와 범위를 드러내는 별도 작업으로 다룬다.
- 팀원의 알고리즘 계산과 함수 이름을 존중한다. 연결에 필요한 수정을 설명하고, 관련 없는 튜닝값·ROI·미검출 정책·기본 선택값을 바꾸지 않는다.
- `center`, 좌우 모드, 0/320 대체값은 현재 basic의 규칙이다. 모든 미래 검출기와 조향기의 공통 규칙으로 강제하지 않는다. 필요한 조합의 입력·출력 의미는 문서와 호출부에서 명확히 한다.
- 검출과 조향이 함께 사용하는 좌표 기준·좌우 모드는 같은 값으로 연결한다. 기존 Sat/Sobel처럼 검출 함수와 `Basic_P.makeTwist(center, lane_mode)`에 해당 프레임의 모드를 인자로 전달한다. 현재 `Basic_P`는 객체의 모드 필드를 읽지 않으므로 호출 전에 필드를 대입하는 방식으로 되돌리지 않는다. 새 분기에서도 인자 전달을 유지한다.
- `Basic_P.Config`의 향후 사용 예정 필드와 주석 처리된 교차로 분기는 사용자가 남겨 둔 확장 지점이다. 미사용이라는 이유만으로 제거하지 않는다.
- 사용자 편집과 기존 미커밋 변경을 먼저 확인하고 보존한다. 작업 이력에 있는 과거 요청이나 다음 작업 목록을 현재의 실행 지시로 해석하지 않는다.

## 호환성과 확인

- Python 3.8에서 동작하는 문법과 라이브러리 API를 사용한다. 예를 들어 `match/case`, `X | None` 같은 새 문법을 도입하지 않는다.
- 의존성을 추가하면 `package.xml` 등 실제 설치 경로를 함께 점검한다. 새 검출 파일만 추가할 때는 기존 `find_packages`가 하위 Python 패키지를 포함하므로 실행 엔트리 포인트를 추가할 필요가 없다.
- 변경에 맞는 확인만 수행한다. 알고리즘 연결을 바꿨다면 선택 전환, 계산 결과, 파라미터, 디버그 영상과 기존 조합의 동작을 확인한다. 구체적인 항목은 기여 가이드에 있다.
- 검증용 속도 출력은 실제 `/cmd_vel`과 구분한다. 입력 오류와 정상 영상의 미검출을 각각 확인한다.
- 문서만 바꾼 경우에는 링크·명령·코드 예제와 실제 소스의 일치를 확인한다. 불필요한 주행이나 전체 빌드를 수행하지 않는다.
- Python 3.8 문법 검사, Humble 실행, 실제 Galactic 실행, bag 검사, 실차 검증을 구분해서 보고한다. 한 가지 검사를 통과했다고 전체 주행 성능을 보장하지 않는다.

## 문서와 보고

- 사용자용 동작·토픽·파라미터·제한점은 README, 이식 절차와 Git 기여 방법은 CONTRIBUTING에서 관리한다. 이 파일에 전체 절차를 중복하지 않는다.
- 구현된 동작, 알려진 문제, 설명용 예제를 구분한다. 문서 속 새 알고리즘 예제는 현재 설치된 알고리즘 목록에 포함되지 않는다.
- 변경 후 수정 파일, 입력부터 출력까지 달라진 흐름, 검증 결과, 남은 한계를 설명한다. 알려진 문제를 수정했다면 해당 문서도 갱신한다.
- 기여는 브랜치에서 작업하고 push 후 GitHub PR로 제안하는 흐름을 따른다. 문서에 적힌 절차만으로 commit·push·PR 실행을 지시받았다고 판단하지 않는다.
